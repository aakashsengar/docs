# System Architecture

This page describes the RadarOS architecture: how packages are organized, how layers interact, and how data flows through the system.

---

## Monorepo Structure

RadarOS is organized as a monorepo with three primary packages. Each package has a focused responsibility and can be used independently or together.

---

## Package Overview

| Package | Purpose |
|---------|---------|
| **@radaros/core** | Agents, models, tools, memory, storage, vector stores, MCP client, A2A client |
| **@radaros/transport** | Express REST API, Socket.IO WebSocket gateway, A2A server |
| **@radaros/queue** | BullMQ background job processing |

---

## Layered Architecture

RadarOS is built in layers. Higher layers depend on lower ones and infrastructure is pluggable.

1. **SDK Layer** — Agent, Team, Workflow. The primary API surface for defining behavior, orchestrating agents, and running workflows.

2. **Engine Layer** — LLM Loop, Tool Executor, Session Manager, User Memory. Core execution logic with automatic retry on transient failures, tool caching, token-based history trimming, reasoning, and cross-session personalization.

3. **Model Abstraction** — ModelProvider interface and adapters. Abstracts over OpenAI, Anthropic, Google, Vertex AI, and Ollama via factory functions.

4. **Protocol Integration** — MCP Client for consuming external tools, A2A Client for calling remote agents.

5. **Infrastructure** — Storage (in-memory, SQLite, PostgreSQL, MongoDB), Vector Stores, and Embeddings. All pluggable.

6. **Transport (Optional)** — Express, Socket.IO, and A2A Server. Expose agents via REST, WebSocket, or A2A protocol.

7. **Queue (Optional)** — BullMQ workers for background job processing.

## Data Flow

A typical request flows through the system as follows:

```text
User Input
    |
Agent.run() / Agent.stream()
    |
buildMessages (history + system instructions)
    |
LLM Loop (with retry)
    |
ModelProvider (OpenAI / Anthropic / Google / Ollama)
    |
Response (text / tool calls)
    |
Tool Executor (if tool calls)
  +-- Local tools (with optional caching)
  +-- MCP tools (external servers)
  +-- A2A tools (remote agents)
    |
Loop until final response
    |
SessionManager.save()
    |
UserMemory.extractAndStore() (async, non-blocking)
    |
Output to caller
```

### Detailed Flow

1. **User Input** — A string or multi-modal content (text, images, files).
2. **Agent** — Receives input, loads session history from SessionManager.
3. **buildMessages** — Constructs the message array: system prompt, session history (auto-trimmed if maxContextTokens is set), current user message.
4. **LLM Loop** — Sends messages to the model with automatic retry on transient failures (429, 5xx, network errors).
5. **ModelProvider** — Translates to the provider API format.
6. **Response** — Either text or tool calls.
7. **Tool Executor** — If tool calls, executes tools, appends results, and loops back to the model.
8. **SessionManager.save** — Persists the new turn to storage.
9. **Output** — Returns or streams the final response to the caller.

## Performance Optimizations

RadarOS is designed for minimal overhead. Key optimizations include:

| Optimization | Impact |
|-------------|--------|
| **Tool schema caching** | Tool definitions are converted to JSON Schema once at construction, not on every LLM roundtrip. |
| **Minimal schema serialization** | Uses compact JSON Schema 7 output, stripping metadata that inflate token counts. |
| **Session read deduplication** | Session data is loaded once per run/stream call and reused for both context and history. |
| **Non-blocking fact extraction** | UserMemory extraction runs in the background without blocking the response. |
| **Smart context deduplication** | When userMemory.asTool() is registered, user facts skip system prompt injection. |
| **Token-based history trimming** | maxContextTokens auto-trims history (oldest first) to prevent context window overflow. |
| **Automatic retry** | Transient LLM API failures (429, 5xx, network errors) are retried with exponential backoff. |
| **Streaming usage tracking** | Token usage is accurately tracked in both run and stream modes. |

## Core Design Principles

- **Zero Meta-Framework Dependency** — No Next.js, Remix, or framework-specific runtime. Use RadarOS with any Node.js server or headless.
- **Optional Peer Dependencies** — Providers (openai, anthropic, etc.) are peer dependencies. Lazy-loaded so you only bundle what you use.
- **Event-Driven** — EventBus emits lifecycle events. Subscribe for logging, analytics, or custom middleware.
- **Pluggable Everything** — Storage, models, vector stores, and transport are all swappable. Configure once, change later without rewriting logic.
- **Open Protocol Support** — MCP for tool integration and A2A for agent interoperability. Connect to the broader AI ecosystem without vendor lock-in.
- **Production Resilient** — Automatic retry with exponential backoff, token-based context trimming, and non-blocking background operations ensure reliability at scale.
